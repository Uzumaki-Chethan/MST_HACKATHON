# SPEC changes

Every deviation from docs/SPEC.md: date, what, why. Append only.

- **2026-09-28 — Scaffold from MST Vibe Kit 0.1.1 (`create-mst-app --template blank`).** Kept its turbo.json, workspace scripts, `scripts/deploy.ts` / `verify.ts` and hardhat networks (`testnet` = 91562037). Restructured to §4.3: frontend moved under `src/`, shared renamed `@nestledger/shared`, backend and firmware folders added. Hardhat bumped to solidity 0.8.24 with `viaIR: true` (§5.1). `Hello.sol` / `useHello.ts` are Vibe Kit samples that WP-A / WP-C will delete.
- **2026-09-28 — Env file location.** The Vibe Kit's hardhat.config reads secrets from the repo-root `.env.local`, not `packages/contracts/.env.local` (§5.10). One root `.env.local` holds all keys; `.env.example` lists every variable.
- **2026-09-28 — 2 laptops instead of 4 people.** See docs/WORK-SPLIT.md. Branches are `lap1` / `lap2` instead of `wp-a..wp-d`.
- **2026-09-28 — Per-laptop notes files.** Root `CLAUDE.md` keeps only the shared rules (Claude Code auto-loads only that name). Laptop-specific approach and sync logs live in `CLAUDE1.md` (Laptop 1) and `CLAUDE2.md` (Laptop 2).
- **2026-09-28 — Manifest access without a context (Laptop 1).** §7.6 only defines lease/project/proposal/society/order contexts. Manifests that carry no context id (lease terms, project/milestone specs, notes, profiles) are readable by their uploader and by any signed-in user. They hold no photos, and their hashes are already on-chain.
- **2026-09-28 — `@nestledger/shared` is `"type": "module"` (Laptop 1).** Required so the backend (tsx, ESM) can import its re-exports at runtime.
- **2026-09-28 — Anthropic provider sends no `temperature` (Laptop 2).** SPEC §6.2 says temperature 0, but current Claude models (default `claude-opus-5`) reject sampling parameters with a 400. Reproducibility still holds because every report is stored with its hash on-chain and never regenerated (§6.1). Gemini still uses temperature 0. A `refusal` stop reason is treated like invalid output: no attestation, humans decide.
- **2026-09-28 — `VisionLLM.analyze` gets an optional `task` field; default `maxTokens` is 16000 (Laptop 2).** `task` tells the `fixtures` provider which `src/ai/fixtures/{task}.json` to return; the real providers ignore it. The 16000 default (instead of 4000) leaves room for the model's default thinking before the JSON answer.
- **2026-09-28 — Frontend reads go through a same-origin RPC proxy (Laptop 2).** SPEC §8.1 has wagmi's transport call `https://testnetrpc.mstblockchain.com` directly, but that RPC sends no CORS headers, so browser reads fail. The Vibe Kit's `/api/rpc/testnet` Next.js route forwards them server-side. Wallet-signed writes still go through BridgeKey's own provider. `wallet_addEthereumChain` still uses the real RPC URL (`addChainParams`).
- **2026-09-28 — `useTx` takes loosely typed contract calls (Laptop 2).** Its params are `{address, abi, functionName, args, value}` without per-ABI inference, to keep the hook simple. Contract reads (`useReadContract`) are still fully typed.
- **2026-09-28 — Testnet v1 is a partial deploy (Laptop 1).** §10.2 plans "testnet v1" after A1. It contains NestRegistry, NestPassport and RentalEscrow only; RentalEscrow's `resolver` and `ledger` are the zero address until the v2 redeploy (A4). On v1, leases must use `flatId 0` and disputed responses revert. v2 redeploys all 8 contracts with full wiring (§5.10).
- **2026-09-28 — Test-only mocks (Laptop 1).** `contracts/mocks/TestMocks.sol` (MockLedger, MockResolver, Actor) lets A1 be tested before SocietyLedger and DisputeResolver exist. They are never deployed.
- **2026-09-28 — Extra HTTP status codes (Laptop 1).** Besides §7.3's 400/401/403/404/500, the backend returns 409 (`/gas/drip` already done), 502 (AI output invalid / drip send failed) and 503 (AI module or contract not available yet), all in the same `{error:{code,message}}` shape. `/timeline` items also carry `contract`.
- **2026-09-29 — Invoice rule R4 and photo reuse checks don't match look-alike templates (Laptop 2).** Measured: two *different* invoices printed from one vendor template have a 64-bit blockhash distance of 0 (6 at 256 bits), so R4's "pHash within 6 of a prior invoice file" would flag every repeat vendor, including the demo's seeded history. R4 now flags: the same vendor + invoice number, an identical file (keccak), or, only when the invoice number is unreadable, a pHash within 6. `checkEvidence` compares a photo's pHash only against other photos, not against invoices or design references (which look alike by construction). §6.5 reuse detection for room and site photos is unchanged.
- **2026-09-29 — Milestone check details (Laptop 2).** One LLM call covers up to 8 vantage points (ref + site = 16 images) instead of batching, since line-item statuses can't be merged across batches; milestones have 3–4 vantages in practice. If any site photo in the claim is reused or not fresh, every line item gets 0 support, because photos can't be attributed to single line items (§6.5 fail-safe).
- **2026-09-29 — Fixtures details (Laptop 2).** `task@variant` picks a per-case fixture (the demo invoices have one each, by rupee amount: `invoiceExtract@1200/1350/1500/4800`). In fixtures mode the invoice justification is the template built from the computed facts rather than a canned sentence, so it never quotes numbers that aren't in the report. PDF-only invoices return 409 ("upload a photo"), as PDF-to-image conversion is P1.
- **2026-09-29 — Capture-session tables (Laptop 1).** §7.4 has no storage for the P1 QR handoff, so two tables were added: `capture_sessions` (token, creator, context, stage, template, expires_at) and `capture_uploads` (token, hash). `GET /capture-sessions/:token` also returns `context`, `stage`, `template` and `expiresAt` alongside `uploads`.
- **2026-09-29 — Keeper uses chain time (Laptop 1).** Deadlines are compared with the latest block timestamp, not the server clock, so keeper decisions match what the contracts will accept.
